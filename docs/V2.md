# LuciaOS v2 — language first

v1 built the whole vertical: a persistent Fabric of Texels, typed
Fibers, capabilities, demand-driven evaluation, a C ABI, and Luce as
the evaluator language on top.  It worked, and it taught us the most
important lesson of the project: **Luce is the part that enables
everything else.**  Every other layer — storage images, texels,
fibers, access rights — made iteration slower while the language was
still growing.

v2 restarts from that first principle.  The v1 tree lives on the
`main-v1` branch and in `docs/v1/`; nothing is lost, and the Fabric
ideas return later on top of a language that has already earned them.

## The shape of v2

Two programs, one language module:

```text
luce  —  the compiler.   FILE.luc  ->  FILE.lc
loom  —  the environment that runs .lc programs.
```

- **`src/luce/`** is the language: indentation-aware lexer → parser →
  analyzer (typing + IR lowering) → verified Luce IR → the backend
  boundary → the deterministic interpreter.  All of it carried over
  from v1 intact, plus `module.zig`, the `.lc` on-disk format.
- **`src/apps/luce/`** is the compiler CLI: `build`, `check`, `ir`.
- **`src/apps/loom/`** is the terminal: a small colored shell that runs
  programs, plus the trusted host behind the Luce host builtins.
- **`programs/`** is userland, written in Luce.  The first citizen is
  the editor.

The language itself — values vs heap objects, collections, explicit
memory, scope, traps — is specified in `docs/LANGUAGE.md`.

Ordinary OS files replace the v1 disk image.  Linux and macOS first;
network, braids, and synchronization stay deferred until the local
story is excellent.

## The .lc module format

`luce build` serializes the verified IR program: constants, struct
layouts, functions (locals, instruction pool, blocks), the port
schema, and the entry point.  `loom` decodes and **re-runs the IR
verifier** before executing, so damaged modules are rejected rather
than run.  The format is versioned (`LUCE` magic + u32 version); any
change to the instruction set bumps the version and stale modules
simply recompile from source.  Treat `.lc` like an executable: the
verifier checks structure, not intent.

## The host boundary

Luce stays pure: every effect goes through a builtin that the host may
or may not provide.  Programs compile with `allow_host`; the pure
`evaluate()` API provides no host, so the same program traps instead
of touching anything.  loom is the trusted boundary that implements:

| builtin | shape | meaning |
| --- | --- | --- |
| `print(text)` | `String -> ()` | console line |
| `arg_count()` / `arg(i)` | `-> Int`, `Int -> String` | program arguments |
| `file_read(path)` | `String -> String` | read a file (traps on failure) |
| `file_write(path, text)` | `-> Bool` | write a file |
| `file_exists(path)` | `String -> Bool` | probe a file |
| `term_rows()` / `term_cols()` | `-> Int` | screen size |
| `term_clear()` | | clear the frame |
| `term_move(row, col)` | | position the cursor (0-based) |
| `term_style(fg, bg, bold)` | `Int, Int, Bool` | 256-color SGR; −1 = default |
| `term_write(text)` | `String` | draw text (sanitized by the host) |
| `term_flush()` | | present the frame |
| `key_read()` | `-> String` | block for one key ("text", "enter", "up", "ctrl_s", …) |
| `key_text()` | `-> String` | payload of the last "text" key |

The host owns raw mode, the alternate screen, buffering, and every
escape byte; a program can never emit control sequences directly
(`term_write` sanitizes).  Raw mode engages lazily on the first
terminal builtin and is always restored before a trap is reported.
`key_read` presents the pending frame before blocking, so a draw loop
needs no explicit flush.

Interactive programs run under an effectively unlimited step budget;
the call-depth limit still catches runaway recursion.

## The editor

`programs/editor.luc` is the proof that the language is enough: a
modern terminal editor written entirely in Luce — movement, editing,
scrolling, line numbers, a status bar, save/quit, and per-line Luce
syntax highlighting (keywords, capitalized type names, builtins,
strings, numbers, comments).  Its source is embedded in the loom
binary, so `loom edit FILE` always works; `LOOM_EDITOR=path/to.luc`
swaps in a different editor without rebuilding, and
`loom run editor.lc FILE` runs a compiled one like any other program.

## What stays deferred

Fabric, Texels, Fibers, capabilities-as-values, Views, the Spool, the
C ABI, braids, multi-user anything.  The v1 fabric *intent* builtins
still exist in the compiler behind `allow_fabric` (off everywhere in
v2), so the road back is paved but nothing in v2 depends on it.

## Roadmap

1. ~~Grow the language where the editor hurts~~ — done: `List`,
   `Map`, `Array` (multi-dimensional), `Builder`, slices, `for x in`,
   explicit `new`/`free` with leak reports, `str`/`parse_int`/
   `parse_float`/`chr`/`ord` (see `docs/LANGUAGE.md`).
2. ~~Modules~~ — done: a file is a module, `import` binds a sibling
   file as a namespace, the whole graph compiles into one .lc, and
   cross-file diagnostics carry their file (see `docs/LANGUAGE.md`).
3. Rebuild the editor's buffer on `List(String)` lines and a
   `Builder` frame — the collections exist now.
4. Grow the terminal: mouse, bracketed paste, incremental drawing
   (damage tracking in the host, same builtins).
5. More userland: `fmt.luc`, `grep.luc`, a file browser.
6. Native code generation behind the same backend boundary.
7. Then — and only then — persistence and the return of the Fabric.
