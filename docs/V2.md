# LuciaOS v2 — language first

This is the product north star. It explains what v2 is for, which parts of the
repository carry it, and what deliberately waits. The current language is in
[LANGUAGE.md](LANGUAGE.md); the remaining work is in
[ROADMAP.md](ROADMAP.md); confirmed defects alone belong in
[MISSING.md](MISSING.md).

## The premise

Luce is the part that enables everything else. A storage system, capability
model, sync protocol, or application framework built while the language is
still changing would turn every language improvement into a migration. The
language and its local toolchain therefore come first. Higher layers arrive
only when they can be ordinary Luce programs and packages rather than special
cases in the compiler.

The product promise is deliberately simple:

> Familiar source, explicit types, native code, automatic memory management,
> and failures that say exactly where they came from.

Luce is pre-1.0. We are using that freedom to simplify and break the language
when the result is better. Compatibility becomes a promise only when the 1.0
contract is intentionally locked.

## The tools

Two commands share one language implementation:

```text
luce  — compiler, test runner, and project/package tool
loom  — interactive shell and loader for optional .lc library artifacts
```

`luce build FILE.luc` creates a native executable by default. `luce check`
stops after semantic validation, `luce ir` makes the internal program visible,
and `luce test` discovers and runs Luce tests. Local package authoring uses
`luce package new` and `luce package version`; publishing remains disabled
until a real registry and trust model exist.

The release also includes:

- `editor`, a standalone terminal editor written in Luce;
- the Luce syntax extension for VS Code, VS Code Insiders, and Cursor;
- the runtime and startup libraries needed by native executables and `.lc`
  libraries; and
- the maintained TermUI package.

## The language module

`src/luce/` is one staged compiler:

```text
UTF-8 source
  → lexer
  → parser
  → semantic analysis and typed HIR
  → mechanical HIR lowering
  → verified MIR
  → optimization
  → LLVM object emission
  → native executable or .lc library
```

The stages are organized by responsibility rather than chronology. Semantic
rules live in `src/luce/runtime/`, shared by the compiled engine and the
interpreter used as a differential test oracle. The interpreter is not shipped
and is never a fallback for unsupported compiled behavior.

[PIPELINE.md](PIPELINE.md), [ENGINE.md](ENGINE.md), and
[CODEGEN.md](CODEGEN.md) own the detailed seams.

## Artifacts and compatibility

A `.lc` is target-specific native machine code in a tagged shared library.
`loom run` validates it, opens it, resolves one entry point, and calls it. The
artifact records the target, host ABI, content identity, and code generator so
a stale or foreign library is refused by name.

Serialized MIR is an internal handoff and cache-key seam. It uses `.lcm` only
when it reaches disk. Decoding always re-runs the verifier. Instruction or
serialized type changes bump the module format; published host-table changes
bump the ABI. The current versions are documented in [CODEGEN.md](CODEGEN.md)
and the public command-line guide.

Neither artifact is a source-compatibility promise. Before 1.0, users rebuild
from current source with the current compiler.

## The host boundary

Luce code never reaches the machine behind the runtime’s back. Console and
environment access, time, process exit, files, directories, terminal input and
drawing, workers, windows, and GPU surfaces all pass through one versioned host
table.

A program compiled without host permission cannot call those effects. A
runtime whose host omits an optional service traps `host_unavailable`; it does
not silently choose another implementation. The shipping native host and
`loom` supply the same table.

The host owns platform mechanisms—file descriptors, OS threads, AppKit, and
Metal. The runtime owns Luce semantics—ARC, errors, traps, worker snapshots,
and resource lifetime. A host callback performs an effect; it does not become
a second implementation of the language.

## The memory model

The current language already follows one rule from a local list to a complete
application:

> Values copy. References share identity. ARC keeps references alive. Weak
> references break cycles. Resources close at the last strong release.
> Workers never share object identity.

Fixed-width numbers, text, bytes, structures, enumerations, and unions are
values. Lists, maps, arrays, classes, files, tasks, windows, surfaces, and
closure environments are references. Classes add shared mutable identity,
definite custom initialization, weak edges, and deterministic `deinit` without
adding inheritance or manual ownership syntax.

Captured closures, bound methods, interface values, errors, optionals,
containers, and worker cleanup all use the same retain/release machinery.
[MEMORY.md](MEMORY.md) is the exact contract.

## Userland proof

The language is proved by applications that are not compiler fixtures.

TermUI 0.3 is a declarative terminal application package. An application is a
class whose `body()` describes a view tree. `Panel`, `HStack`, `VStack`,
`ZStack`, `Label`, and `Rows` are ordinary Luce values; bound class methods are
ordinary event callbacks. `termui.run(application)` owns raw mode, the
alternate screen, layout, rendering, input, resize, cursor placement, and
restoration.

The editor uses that public surface. Its mutable model is a class, its view is
rebuilt from current state, and the application loop is not present in editor
source. Scripted editor behavior runs on both engines, model tests run through
`luce test`, and the release gate compiles a standalone editor product.

This proves the current class/interface/closure model in terminal userland. It
does not claim that the low-level `std.ui` and `std.gpu` modules are already a
native UI framework.

## What remains before the language can settle

The complete audit and order are in [ROADMAP.md](ROADMAP.md). No additional
language feature is required before the first release. User-defined
monomorphized generics with interface bounds remain a post-1.0 proposal;
interfaces already use one owned existential payload and witness identity,
including writing value-structure witnesses behind `mutating` requirements.

After those, ordinary packages can provide typed data structures and a native
declarative UI layer. Registry publishing, other platform installers, Vulkan
hosts, and optional syntactic conveniences are separate product or ergonomics
work, not hidden prerequisites for ARC, classes, closures, or TermUI.

## What stays deferred

Persistence images, a capability system, network synchronization, braids, and
multi-user collaboration wait until the local language, packages, native UI,
and toolchain are excellent. Shared mutable heaps, unsafe pointers, class
inheritance, reflection, macros, and a tracing collector are deliberate
non-goals for the current roadmap.

The sequence matters: every higher layer should make Luce easier to trust, not
make the language harder to change.
