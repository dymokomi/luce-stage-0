Luce squares an i64 with checked signed 64-bit multiplication. A representable product is returned; an out-of-range product raises the integer-overflow trap.

Follow one multiplication

This program squares a value that is unknown until launch. Look for multiply.i64 in MIR, llvm.smul.with.overflow.i64 in LLVM IR, and the multiply-plus-overflow branch in ARM64. Those are three spellings of the same language promise.

their IEEE format and behavior

An unconstrained integer literal defaults to i64; an unconstrained floating literal defaults to f64. Context may give a fitting literal another numeric representation when semantic analysis first assigns its type.

How numeric representations change

Two concrete operands in one arithmetic operation have the same type. A constructor such as i64(small) marks a representation change and selects its overflow, comparison, and precision behavior.

Checked integers

Addition, subtraction, multiplication, division, remainder, negation where available, and shifts enforce their type's bounds. Overflow, division by zero, the signed minimum divided by -1, and an invalid shift count each produce a stable trap code.

Defined

Every integer input either produces the exact same-width result or a named trap.

Overflow path

An out-of-range result branches to the named integer trap for that operation.

Floats keep their width

Floating arithmetic follows the chosen IEEE format. A f32 operation uses f32 precision. Integer/floating constructors perform representation conversion, and an unrepresentable conversion raises its defined trap.

Bits are for integers

Bitwise operators apply to concrete integer types. Shift amount checks are width-aware. Precedence is fixed by the expression parser, and compound forms follow the same checked operation plus assignment transaction as their expanded spelling.

The implementation path

Semantics lands literals, checks same-type operands, and records explicit conversions. MIR carries exact-width types and operation tags. The runtime implements checked operations once; generated code may inline an operation only while preserving the same trap edge. Both paths compare the trap and result in specs.
