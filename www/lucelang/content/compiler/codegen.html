Code generation translates every verified MIR instruction into LLVM IR. For checked multiplication, that means a product plus an overflow bit and an explicit branch to Luce’s trap path.

Compare MIR, LLVM IR, and assembly

The middle two tabs show the transformation this page explains. MIR says multiply.i64. LLVM expands the check with llvm.smul.with.overflow.i64. The final ARM64 performs the same check with flags and a branch.

The backend pipeline

Every instruction has an arm

The lowering switches enumerate every MIR instruction and intrinsic tag. Adding a tag makes those switches incomplete until its LLVM representation is implemented. A target limitation returns a named unsupported result, and malformed MIR fails verification before lowering.

Why totality matters: the host language’s exhaustive switch turns a new MIR instruction into a compile error at every backend location that needs its native meaning.

Runtime calls and inline work

Generated code keeps plain scalar control and representation work inline where that is both safe and visible to LLVM. Dynamic language semantics call libluce_rt: ARC, heap resolution, container mutation, text storage, checked operators, workers, resources, and trap construction.

Inline LLVM

Branches, arithmetic with its trap edge, loads and stores, stack slots, optional tags, direct calls, and indirect calls.

Runtime boundary

Heap identity, reference counts, moving container buffers, UTF-8 storage, host-backed handles, worker transfer, and shared trap state.

Runtime effect metadata

LLVM optimizes a call more accurately when it knows which memory the callee reads or writes and whether it returns or unwinds. runtime_effects.zig describes those properties for the C exports. Tests compare the metadata with the Zig declarations and report any divergence.

Runtime services and host services

Lists, strings, ARC, and arithmetic are language semantics and therefore runtime calls. Console, files, clocks, terminals, processes, sockets, windows, and other outside effects arrive through the versioned LuceHost table. Each optional service fails closed when absent.

How loom delegates cold compilation

LLVM IR construction uses a vendored pure-Zig builder, and codegen/emit.zig calls libLLVM. The luce compiler imports that emission module. loom loads existing machine code and invokes the sibling luce binary for a cold compile.
