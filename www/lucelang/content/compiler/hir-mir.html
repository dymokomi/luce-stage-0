HIR is the checked version of the source tree

HIR keeps loops, matching, compound and parallel assignment, optional control, resolved calls, and capture environments. It adds resolved types, store kinds, temporary parks, receiver effects, and source origins.

StructuredA loop remains a loop and a match remains a match.
TypedEvery expression and place has one resolved type.
ResolvedCall targets, captures, ownership, and host effects have concrete representations.
Ready to lowerThe source-level checks have completed before register and block construction.

How structured HIR becomes blocks

hir/lower.zig walks the checked tree and calls the MIR builder. It splits structured control into blocks and expands compound operations using decisions already recorded in HIR. A missing lowering indicates that HIR or the lowering implementation lacks a required case.

MIR’s execution vocabulary

A mir.Program holds declarations, value and heap layouts, constants, functions, typed registers, locals, basic blocks, and source origins. Each block ends in a terminator. Retain, release, and storage-drop instructions carry reference ownership into both execution paths.

Use the instruction guide above the MIR file to follow local_get, local_set, branch, and drop_storage. Together they show where values live, which block runs next, and when temporary storage is released.

What MIR verification checks

The verifier checks register indices and types, local and layout consistency, block termination, branch targets, call shapes, instruction legality, weak and worker boundaries, ownership claims, and source tables. Generated MIR is verified before and after optimization. Decoded MIR is verified before any engine sees it.

The verifier works from MIR facts. It checks that a retain names a reference register. Binding mutability was already checked from the source declaration and expressed in the generated store sequence.

Why MIR can be saved and loaded

MIR encodes deterministically as an internal .lcm handoff and cache identity. Its format in the committed source snapshot is @mir_version@, read from mir/module.zig at site build time. A format mismatch causes the cache to compile again from source.

Changing an instruction, intrinsic, type tag, trap or error code, encoded layout field, or another wire meaning bumps the format and updates the fingerprint and hostile decoder tests together.
