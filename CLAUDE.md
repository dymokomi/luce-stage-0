# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Workflow

Single-developer project: commit directly to `main` (no PRs, no feature branches) with git author `Dy Mokomi <dy@dymokomi.com>`.

## Build and test

Everything is Zig 0.16 (pinned in `build.zig.zon`) and runs on any host OS:

```sh
./build.sh         # zig build --prefix build: the terminal lands at build/lucia, libloom.a at build/lib/
zig build test     # engine suite + Luce suite + terminal suite + C ABI smoke test
zig fmt loom/ luce/ apps/lucia/ build.zig
```

Tests are `test` blocks beside the code they prove, leak-checked under `std.testing.allocator`; `zig build test` discovers them through the module roots (`loom/loom.zig` re-exports every engine package and references `loom/first_lucia_test.zig`; `luce/luce.zig` and `apps/lucia/main.zig` do the same for their trees). A new engine package must be added to `loom/loom.zig`'s re-exports and test block (same pattern for `luce/`). `loom/first_lucia_test.zig` is the acceptance test proving the full flow from `docs/LOOM.md`. Note: `zig build test` does not refresh installed binaries — run `./build.sh` for that (a bare `zig build` installs under `zig-out/` instead; both install trees are gitignored).

## What this project is

LuciaOS is building **Loom**, a single-user local engine for a persistent **Fabric** of identity-bearing **Texels** connected by typed **Fibers**. The user-visible ontology is deliberately tiny (Texel, Port, Fiber, View); everything else is implementation machinery. Read `docs/LOOM.md` before making architectural decisions — it is the north star, and "if a change makes the architecture harder to see, do not merge it."

Deferred by design (do not build toward these): production security, multi-user collaboration, Braid synchronization, permanent history, replacement evaluation engines, and the agent.

## Architecture

Strict layered dependency chain — lower layers must not know about higher ones, and storage must stay independent of Fabric concepts:

```text
projection / view → evaluation → organization / fabric → storage
tests → the package under test
```

The engine lives under `loom/`, one package per directory, re-exported by `loom/loom.zig`:

- **`loom/storage/volume.zig`** — fixed-size page stores. `Volume` is a tagged union (real substitution: `FileVolume`, `MemoryVolume`); `FileVolume` carries its explicit `std.Io` — the rest of the engine never touches the host. **This package is the reference coding style — match it.**
- **`loom/fabric/`** — `texel_id.zig`, `value.zig` (tagged-union `Value`, `BlobRef`), `texel.zig` (`Texel`, `InputPort`, `OutputPort`, `Fiber`; ports live in name-sorted tables). `InputPort` and `OutputPort` are distinct types because they own different state: an InputPort owns its single incoming Fiber binding; an OutputPort owns its value/revision state and may fan out to many inputs. `encode.zig` is the frozen LUTEXEL snapshot encoding; `store.zig` is `Store` (durable Texel snapshot using two descriptor pages and two body arenas, published atomically by generation) and `Transaction` (private working snapshot; `connect`/`disconnect`/`put`/`putBlob`, visible only after `commit`). Large content goes out of line as blobs behind `BlobRef`.
- **`loom/evaluation/`** — `spool.zig`: demand-driven, cached, acyclic evaluation. `Spool` is a *disposable* cache over a read-only `Store` plus a non-owning `Registry`; evaluators are pure and keyed by persisted name. `fiber_index.zig` is the disposable reverse index. Recurrence only enters through explicit State/Delay (`state.zig`).
- **`loom/organization/arrangement.zig`** — arrangements (Texels whose inputs name/order other Texels), LARR encoding.
- **`loom/effects/effect.zig`** — effect intents as data, performed once at a trusted boundary, receipts replayed forever after.
- **`loom/authority/capability.zig`** — capabilities. Sensitive operations require an explicit capability value arriving at an Input Port; there is no ambient access.
- **`loom/view/`** — Views are ordinary Texels whose computation produces an interface: `evaluators.zig` renders prose/table interfaces from name-sorted text inputs; `shell.zig` is the small trusted shell that demands, composites, and routes edits back as ordinary transactions.
- **`loom/projection/`** — manifest-driven projection of a Fabric region into host files for existing tools (`manifest.zig` validates the output-to-filename map; `projection.zig` exports/imports through explicit `std.Io` with symlink/hard-link/unexpected-file guards).
- **`loom/abi.zig` → `abi/loom.h`** — the constitutional C border for platform shells written in other languages (Swift, Objective-C++, browser engines). Operation-style transactions, emit-callback evaluators (no allocation crosses the border), and the passthrough convention: declared outputs an evaluator does not emit fall back to their stored sources behind the border. `abi/smoke_test.c` drives the whole client lifecycle from C under `zig build test`. The on-disk image format is frozen — the golden fixture `testdata/golden_store.bin` (written by the original C++ implementation before it was retired) must always open unchanged.

**Luce** (`luce/`, its own module; plan and status in `docs/LUCE.md`) is the small, statically typed, Python-looking-but-not-Python language for Texel evaluators. A Texel owns Luce source as *content*; the Texel's Port schema — not the source — decides which `input.NAME`/`output.NAME` members exist. Pipeline (`compile.zig`): indentation-aware lexer → recursive-descent/Pratt parser → arena AST → `analyzer.zig` (checking and IR lowering in one walk: no implicit conversions, immutable `let`, no shadowing, return paths, struct cycles, builtin typing) → typed Luce IR (`ir.zig`: instruction pool + basic blocks; registers never cross blocks, mutable locals carry loop state; verifier + deterministic printer) → the execution boundary (`backend.zig`): immutable Input frame, scratch Output frame, explicit step/depth budget, publish-nothing-on-failure. The first engine behind the boundary is the deterministic IR interpreter (`interpreter.zig`: checked integer arithmetic, IEEE floats, range-checked `Int(Float)`, traps with stable codes); the plan's LLVM lowering slots in behind the same boundary later. Diagnostics carry stable codes (`luce.lex.*`, `luce.parse.*`, `luce.sema.*`) and byte spans.

Direction of demand is opposite to direction of value: a View demands an output, the Spool pulls upstream outputs, runs evaluators, and caches by revision. Nothing recomputes merely because it exists. The engine is an explicit hybrid per `docs/EVALUATION.md` — **"Push invalidates. Pull evaluates."** (LOOM.md principle 8), implemented as: every `Transaction` records the `TexelId`s it touched and `Store` keeps them in a bounded `ChangeSet` ring (`changesSince`; a too-old baseline means rebuild); `Store.observe` is the volatile push path (in-memory value + revision + logical generation bump, nothing durable — reopen reverts to the last durable snapshot); `FiberIndex` expands a delta into a conservative texel-granular dirty closure; `Spool.advance(from, to, dirty)` stamps clean cached records so clean demands are O(1) while dirty paths revalidate lazily with early cutoff intact. Only demand roots evaluate: one-shot `pull`, event-activated `watch`, standing presented Views, and later scheduled demand.

The `lucia` app (`apps/lucia/`, a Zig executable speaking the engine module directly) has two boundaries: a setup boundary (`lucia create IMAGE [--pages N]`) and a load boundary (`lucia open IMAGE`) that drops into an interactive terminal (`lucia>` prompt) over the opened Fabric. The terminal keeps a **selection** (`Session` in `session.zig`: the store, the spool, the selected `TexelId`, and the watch list); `new` auto-selects its texel, the prompt shows the selection (`lucia sum>`), and most commands operate on the selected texel. Commands, each with a short alias: `new NAME` (`n`), `select ID|NAME` (`s`), `show` (`sh`), `rename NAME` (`rn`), `find TEXT` (`f`), `delete` (`rm`), `input NAME TYPE` (`in`), `output NAME TYPE` (`out`), `move DIR OLD NEW` (`mv`, port rename — rewrites downstream Fibers when an output is renamed), `drop DIR NAME` (`dr`, port delete — refused while an output has bound consumers), `connect INPUT ID OUTPUT` (`c`, binds a selected input to a source output; ID may be a unique name; types must match), `disconnect INPUT` (`dc`), `set NAME VALUE` (`se`, typed source value on a selected output), `eval NAME` (`e`, assigns a registered evaluator: `concat`, `sum`, `upper`, `luce`), `code` (`cd`, collect-mode Luce source entry: lines accumulate until a single `.` commits them as the selected texel's content, with compile diagnostics reported immediately), `pull OUTPUT` (`p`, one-shot demand through the session Spool), `watch OUTPUT` (`w`, prints now and again whenever a change moves the value) / `unwatch OUTPUT` (`uw`), `list` (`ls`), `help` (`?`), `exit` (`q`). After every dispatched line the terminal *reconciles*: `changesSince` → `FiberIndex` dirty closure → `Spool.advance` → re-demand only dirty watches, printing those whose outcome moved. TYPE is `bool|int|real|text|bytes|texel|blob`; DIR is `in|out`. A texel's name is deliberately not part of identity — it is a text value on the `name` Output Port. App evaluators live in `evaluators.zig`; because the Spool requires every declared output, any output an evaluator does not emit falls back to its stored source (the passthrough convention), which is how the `name` port rides beside computed outputs. **Boundary texels** (`boundary.zig`): `lucia open` ensures `keyboard` (`line` text, `count` int) and `mouse` (`x`/`y` real, `button` int) exist; every line read records a *volatile* keyboard observation via `Store.observe` before dispatch — push refreshes boundary observations and marks dirt, demand pulls them, and observations become durable only when a later commit snapshots them. The app is organized as `main.zig` (create/open dispatch), `command_line.zig` (process-argument parser plus `splitWords`, a quote-aware line tokenizer), `session.zig` (terminal state, including in-progress code collection), `terminal.zig` (the read-dispatch loop; prompt only when stdin is a tty; also the in-process scripted-session tests), `luce_service.zig` (the `luce` evaluator: compiles texel content against the texel's own ports, caches the verified program by texel revision — derived and disposable — and runs it through the backend boundary; traps and compile failures become error outcomes, unwritten outputs pass through stored sources), `command.zig` (the `Command` table-entry struct: name/alias/argument_count/usage/run), `command_set.zig` (the dispatch table; arity-checks and prints usage), and `commands/` (one file per command, named after the command alone — `commands/new.zig` — plus `commands/common.zig` shared helpers). To add a terminal command: create its file in `commands/` exporting `pub const entry: command.Command` and add it to the table in `command_set.zig`.

## Coding conventions

`docs/CODING_GUIDE.md` is authoritative and intentionally opinionated — plain, old-school code over clever ceremony, now expressed in Zig. The essentials:

- Zig 0.16; `zig fmt` before every commit; errors as values with small explicit error sets; no panics for ordinary failure; never hide durability (callers call `flush()`).
- Allocation is explicit: functions that allocate take an `Allocator`; every heap-holding type has `clone` and `deinit`; doc comments say who owns what and what invalidates borrows. Tests run leak-checked under `std.testing.allocator`.
- Anything host-facing takes an explicit `std.Io` (`FileVolume`, `FileProjection`, the terminal); the rest of the engine never touches the host. The scheduler and evaluation semantics belong to Loom, never to Zig async.
- Tagged unions over class hierarchies (`Volume`, `Value`, `Outcome`); function-pointer tables only where substitution is real (`Evaluator`). No comptime cleverness a reader can't hold in their head, no premature abstraction, no framework-style managers.
- Naming: TitleCase types, camelCase functions, snake_case fields; short verbs (`read`, `write`, `open`, `parse`, `encode`); collections use `count`/`has`/`get`/`put`/`remove`/`at`; drop redundant type nouns (`volume.read(...)`, not `readPage`); plain-English names (`file_handle`, `page_index` — never `fd`, `buf`, `n`, `ptr`).
- Comments: `//!` file purpose lines, dashed section headers, `///` docs that explain assumptions and ownership — not narration of obvious code.
- Keep the hot path visible: `@memcpy`, positional reads/writes, explicit `sync`; no hidden allocations in `read`/`write`; page size is fixed (`page_size`).
- Types that must not move after setup (something captured a pointer into them) use the documented in-place `setup(self: *T, ...)` pattern — `Shell`, `Terminal`, test rigs.
- Tests: `test` blocks beside the code, named after what they prove (`test "file volume persists across close and reopen"`); direct `std.testing` checks, no framework; cover success, bounds failure, and reopen/persistence where relevant.
